Module 13: Network Automation and Programmable Interfaces

1. Introduction

This module closes the course by removing the last assumption still standing. Every command in the previous twelve modules was typed by a person. That is how networks were operated for thirty years, and it remains how most small networks are operated today. It stops working at a size this course has already hinted at twice: in Module 10, where nobody logs into two hundred switches each morning to check whether anything failed, and in Module 11, where one of the commonest faults was nineteen switches configured from a template and the twentieth configured from memory.

Automation addresses both. A script reaches two hundred devices in the time a person reaches two, and it types the same thing on every one of them. The consistency matters more than the speed. A person performing the same task forty times will do it thirty-nine times correctly, and the fortieth becomes a fault someone investigates months later. A script either does it correctly everywhere or fails everywhere, which sounds worse and is considerably easier to diagnose.

Module 12 established what makes this possible: a controller presents a programmable interface northbound, and increasingly individual devices do the same. This module is about using those interfaces, and about the older technique that works when they are absent. Both are worth knowing, because a real network contains equipment of several ages and an administrator does not get to choose. This module covers why automation is worth the effort and what it costs, the two ways a script can reach a device, the structure of a programmable request, the data format these interfaces exchange, the safeguards that separate a useful script from a dangerous one, and how to verify that an automated change actually happened.

2. Real World Scenario: The Same Change, Sixty Times

A policy decision at St. Cloud Technical & Community College requires a new segment for laboratory equipment on every access switch in the campus, sixty of them, each needing the same virtual network created, the same ports assigned, and the same filtering statement added. Performed by hand at four minutes a switch, this is a full day of work that cannot be interrupted, and the probability that all sixty end up identical is not high.

A second requirement arrives at the same time from an audit. The auditor wants evidence that every device in the campus points at the approved time source and sends its logs to the approved server, which are the settings configured in Module 10. Nobody can produce that evidence, because producing it means logging into sixty devices and reading two lines from each, and by the time the last is read the first may have changed.

Both problems have the same shape: the same small operation repeated across many devices, where doing it by hand is slow, error-prone, and unverifiable. The administrator writes a script. The audit request becomes a read-only script that visits every device, retrieves two values, and produces a table, which is also the safest possible first automation because it changes nothing. The configuration change is written afterwards, tested on one switch, and only then released to the remaining fifty-nine.

4. Domain Specific Definitions

  • Application Programming Interface: A defined way for one piece of software to ask another to do something or report something.
  • REST: An architectural style in which each thing a device exposes is addressed as a resource by a web address and acted on with standard verbs.
  • Resource: One addressable item exposed by an interface, such as a single interface, a routing table, or the whole configuration.
  • Verb: The part of a request stating what to do, with GET reading, POST creating, PUT replacing, PATCH altering part, and DELETE removing.
  • Status Code: The number returned with every response stating whether the request succeeded, was rejected, or failed on the device.
  • JSON: A text format representing data as named fields, lists, and nested objects, which software can parse without ambiguity.
  • Data Model: A formal description of what values a device exposes and how they are structured, which allows a program to know what to ask for.
  • NETCONF: A protocol for reading and changing device configuration as structured data over a secure session.
  • RESTCONF: The equivalent expressed as web requests, which makes it accessible to any tool that can make a web request.
  • Screen Scraping: Automating a device by sending command line commands over a session and extracting values from the text returned.
  • Idempotent: Describing an operation that produces the same result whether it runs once or fifty times, which makes a script safe to re-run.
  • Source of Truth: The authoritative record of what the configuration should be, against which devices are compared and corrected.
  • Configuration Management Tool: Software that applies a described desired state to many devices, handling connection, ordering, and reporting.

5. Core Operational Concepts and Architecture

To automate a network safely, an administrator must choose a way to reach the devices, construct requests correctly, read the answers properly, and build in the safeguards that keep a mistake from being applied everywhere at once. The detailed operational breakdown of these components and their technical purpose is detailed below.

A. What Automation Buys, and What It Costs
Four benefits are worth naming separately. Speed is the obvious one and the least important. Consistency is the valuable one: a script applies identical configuration everywhere, which eliminates the entire class of fault that arises from a person doing the same thing slightly differently on the fortieth device. Auditability follows, because a script that reads configuration from every device produces evidence nobody could assemble by hand. And repeatability means the same work can be done again next year, or by someone else, without depending on anyone's memory.

The cost must be stated with equal clarity. A mistake typed at a console affects one device, and the person notices immediately. The same mistake in a script is applied to two hundred devices in seconds, correctly and identically, before anyone can intervene. Automation multiplies whatever it is given, including errors, and every safeguard described later in this module exists because of that one property.

B. Two Ways to Reach a Device
A script can reach a device the same way you do, by opening a secure session, sending commands, and reading the text that comes back. This works on every device that accepts a login, including equipment far too old to offer anything else, which is why it remains widespread. Its weakness is that the text was formatted for a person. The script locates values by their position in the output, and a software upgrade that adds a column or reorders a line silently breaks it, sometimes by producing a wrong answer rather than an obvious failure.

The second way uses an interface designed for programs. The device returns named fields rather than a formatted page, and the script asks for a value by name. Adding information to the response does not break anything, because a parser reading a named field is indifferent to what surrounds it. The limitation is availability: this requires a device new enough to offer the interface and configured to enable it. In practice a campus contains both kinds of equipment, and an administrator uses whichever a given device supports.

  • restconf : Global configuration command that enables the web based programmable interface on releases that support it.
  • ip http secure-server : Enables the secure web service the interface depends on, without which the interface is configured and unreachable.

C. The Structure of a Request
A request has four parts and each answers a different question. The verb says what to do. The address says which resource to do it to. The headers say what format the answer should take and who is asking. The body, present only when something is being created or changed, carries the new values.

The verbs divide usefully into one that is safe and several that are not. Reading changes nothing and can be repeated without consequence, which is why every automation effort should begin there. The others alter the device, and the differences between them matter: replacing a resource discards anything the new content does not mention, while altering part of it leaves the rest alone. Choosing the first where the second was meant is how an automated change removes configuration nobody intended to touch.

D. Why the Data Format Matters
The format these interfaces exchange represents data as named fields, lists, and nested objects. Its importance is not the syntax but what the syntax makes possible. A value retrieved by name is stable. A value retrieved by counting characters into a line of formatted output is not, and the difference becomes apparent the first time a device is upgraded.

The structure also travels in both directions. The same format that describes what a device currently holds describes what it should hold, which is what allows a desired configuration to be written in a file, compared against reality, and applied where the two differ. That comparison is the basis of the configuration management tools an administrator meets after this course, and it is why the format is worth understanding rather than merely tolerating.

E. Writing a Script That Is Safe to Run
Five practices separate automation that helps from automation that causes an outage, and none of them is about programming skill.

Read before you write. The first script against any network should retrieve information and change nothing, which builds confidence in the connection, the credentials, and the parsing without risking anything. Test against one device. A change released to one switch that turns out wrong is a five minute correction; the same change released to sixty is an incident. Make operations repeatable. A script that can be run twice without doing harm can be re-run after a partial failure, whereas one that appends a line every time it runs produces a configuration full of duplicates. Keep the scripts under version control, so that the change to the network and the change to the script that made it are both recorded. And keep credentials out of the file, because a password written into a script is a password given to everyone who can read it, including everyone who can read the repository it is stored in.

A sixth practice deserves its own sentence. Know how to undo it. An automated change should be accompanied by an automated reversal written at the same time, while the intent is still clear, rather than composed under pressure once something has gone wrong across sixty devices.

F. Verification
Verification in this module has a failure mode the earlier modules did not. A script can report success while having achieved nothing, and it will do so whenever it checks that it received a response rather than checking what the response said. The status code is the first thing to read, every time, and a script that does not examine it is not verifying anything.

Beyond the code, three checks are worth making. Read the resource back after changing it and confirm the value is what was sent, which catches a request that was accepted and interpreted differently from what was intended. Confirm on the device itself with the command line commands from the whole of this course, because the device's own view is the authority and a programmable interface is only a way of reaching it. And confirm on a device that should not have changed, which catches a script whose target list was wrong.

  • show running-config | include ntp : Filters the configuration to the lines of interest, which is how a change made by a script is confirmed at the device.
  • show ip interface brief : Confirms at the device what an automated read reported, using output you have relied on since Module 4.

6. Request and Response Reference

This module introduces little device configuration, so the reference below records the two things you will be asked to apply: what each verb does to a resource, and what each family of status codes means.

Description: This matrix details the request verbs, their effect on a resource, and whether an operation is safe to repeat.
Verb Effect on the Resource Safe to Repeat
GET Reads it and changes nothing Yes
POST Creates a new item within it No, a second run may duplicate or be refused
PUT Replaces it entirely, discarding what is not mentioned Yes, with the same content
PATCH Alters the parts named and leaves the rest alone Yes, with the same content
DELETE Removes it Yes, though a second run reports it is already gone
Description: This matrix details the status code families and what each requires a script to do next.
Family Meaning What the Script Should Do
200 to 299 The request succeeded Continue, and read the resource back to confirm
400 to 499 The request was wrong or unauthorized Stop, because repeating it will fail identically
500 to 599 The device failed to carry out a valid request Stop and investigate the device, not the script
